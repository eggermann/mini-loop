# Mini-Loop orchestration

This is the subgoal workflow within `auto`. The coordinator owns the parent GOAL, assignments, decisions, and integration review. Workers report through shared project memory. Continue while verified progress is possible. Pause for a decision that changes scope, requires user authority, or resolves a blocker that the workers cannot handle safely.

- A **subgoal** describes the assigned work and its acceptance criteria. Its context lives in project memory.
- A **worker ID** identifies a logical participant within the run. Its registry record tracks slice status and checkpoints for the assigned work.
- A **runtime session** is where the worker executes. Its binding is the tuple of runtime label (`backend`), host, and handle. The execution environment supplies these values and controls startup, follow-ups, and interruption. The registry stores the binding and manages the same worker state transitions for every runtime.

## Start or resume

When the coordinator handles subgoals directly, record scope, criteria, and handoffs in their Markdown contexts. Use the worker registry below for delegated work and to resume an existing registered run. Resolve the application and MLMS repository as described in the skill. Use Python 3.8 or later and run `python3 <skill-dir>/bin/orchestrate.py <checkout> <run-id> <command>`. In a source checkout the helper is `orchestrate.py` at the repo root. Persist the stable run ID with the parent GOAL in parent active context. The helper keeps `orchestration/<run-id>/run.json` under the resolved MLMS root with atomic updates under the shared lock.

- Use `init "<parent goal>"` before dispatching the first worker. Document the parent's verification criteria. To resume, use `status` on the same run for a compact view of open workers and keep its returned `cursor`. Preserve the run ID, pause, and participant count across resumption.
- Split independent work into subgoals with expected outputs, testable criteria, prerequisites, and file ownership. When delegation is authorized, dispatch independent subgoals with distinct branch/worktree assignments in parallel. Fill available slots before waiting and refill them as prerequisites are met. Keep dependent work queued until its inputs are ready, and run subgoals sequentially when edits cannot be isolated. Verify that every worker resolves the same MLMS root before work. Only the coordinator dispatches workers.
- The limit is 100 participants per run including the coordinator. Use `reserve <worker> "<subgoal>"` **before** starting a runtime session for a new worker. All reservations count throughout the run, including cancelled and archived ones. Resume existing workers when practical. At the limit, continue with existing capacity or pause if a new worker is necessary. Up to three workers may hold active slices at once. JSON retains the legacy keys `chat_limit` and `chats_counted` for compatibility; they count participants across all runtimes.

## Dispatch and monitor

- Start workers through an authorized mechanism provided by the execution environment. This can be a Codex chat, subagent, CLI process, local agent, or external runtime with access to the assigned checkout and shared MLMS root. Use user-owned Codex chats only when the user explicitly authorizes creating them for this work. Follow the chat tool's authorization and worktree rules for creation, assignments, and follow-ups. Keep work with the coordinator when delegation is unavailable.
- At startup, give the worker the parent goal in one sentence, its subgoal and criteria, scoped checkout, run ID and worker ID. Tell it to wait for its registered assignment before changes. Once the actual runtime handle is available, call `bind <worker> <backend> <handle> [--host <host>]`. Use a consistent runtime label such as `chat`, `subagent`, or `cli` and a handle unique to the session within that runtime and host (`local` by default). A binding can only be registered once per run. For queued setup, retain the receipt and wait for the real handle. Settle the existing reservation before retrying startup. Send the current epoch and worker's last ticket from `status` with each assignment. Run `begin <worker> <epoch> <previous-ticket>` before work, using `0` for the first slice. Save the new ticket returned by `begin`. Keep pending dispatches and active slices within the three worker slots.
- Each assignment covers one small slice. Before each editing or side effect batch, use `guard <worker> <ticket>`. When refused, finish only the checkpoint and end the turn. Acknowledge a pause as soon as safely possible. Avoid long-running commands that delay a checkpoint. Guard checks are cooperative and cannot stop a tool call already running.
- End each slice with `report <worker> <ticket> idle|blocked|candidate`, passing JSON through stdin. Use short entries such as `{"summary":"Added branch lookup","evidence":"resolver probe passed","progress":"2/3 verified","next":"check detached HEAD","blocker":""}`. Cite artifacts or checks when available. Keep full logs in their original output. `candidate` requires evidence and `blocked` requires a reason. Hand control back with a brief receipt and wait for the next assignment. The coordinator owns updates to the parent's Memory Bank.
- The CLI makes up to three attempts on lock contention. If it still returns exit `75`, keep the checkpoint and inspect the lock owner. Retry with the same ticket after the lock is available. Never remove a lock until you have confirmed the owner and its updater process have stopped.
- After a restart or lost reply, read `status` for the same run and `status --worker <id>` before retrying. Check the active ticket, recorded checkpoint, or archived review to see whether the command took effect. A duplicate report or acceptance is rejected. If a runtime stopped without a report, confirm it stopped before recording an interruption for that ticket.
- After the first snapshot, poll with `status --since <cursor>` to see only workers changed since the last poll. Use the new cursor for the next poll. Each row shows the subgoal, status, and latest checkpoint when available. Use `status --worker <id>` for one worker's history and `status --full` for the entire run including archived details. Use the worker runtime's wait tools when available. The coordinator surfaces decisions, blockers, and verified outcomes. Review the next assignment when two slices in a row show no new verified evidence or resolved blocker.

## Pause all workers for a decision

1. Call `pause <epoch> "<specific decision and reason>"` with the current epoch before requesting user input. This seals new reservations, new slices, and further guarded editing batches for this run. The coordinator stops dispatching and implementing. Ask active workers to checkpoint and stop their slices using an authorized control channel. Workers that see the pause report without waiting for a separate message.
2. Give active workers one bounded wait for reports. If a worker keeps running, use its runtime's interruption capability when available and authorized. If a sidebar chat cannot reach a checkpoint and has no direct interrupt tool, show its actual state so the user can stop it in the app. Keep queued setup visible until it binds and stays idle or is confirmed cancelled. After verifying the exact slice has stopped, record `interrupt <worker> <ticket> "<verified stop evidence>"` to settle a missing report. Retain its previous checkpoint and treat it as potentially stale. For out-of-scope work or confirmed failed setup, use `cancel <worker> <worker-revision> "<reason and evidence>"` with the revision of the worker state you reviewed. Never report an active or unverified worker as paused.
3. Fetch a fresh `status` snapshot so unchanged affected workers are included. The coordinator asks the user once, with the decision, options and tradeoffs, and one short line per affected worker giving progress, evidence, blocker, and last known activity. Identify any worker with an unconfirmed stop or requiring manual interruption. Keep the run paused while waiting.
4. After an explicit user decision, confirm that affected workers have stopped their slices and pending setups have settled. Then record `resume <epoch> "<actual user decision>"` using the epoch of the pause the user answered. This advances the epoch so old assignments cannot start. Update parent decisions and dispatch with the new epoch. Elapsed time or silence does not authorize resumption.

## Accept and integrate

Review each `candidate` against its assignment, checks, and integration needs. The registry records worker claims, coordinator evidence, and acceptance decisions separately. It checks the text and transition preconditions. The coordinator checks the actual artifacts or results independently. If a required check failed or was not run, record that and use `rework <worker> <ticket> "<correction>"`. Otherwise, call `accept <worker> <ticket> "<independent review evidence>"` with the ticket you reviewed. After acceptance, record the verified result in the parent's `memory-bank/progress.md` under the shared lock, including worker ID, subgoal, and any outstanding integration. If interrupted between acceptance and the memory update, recover the checkpoint and review with `status --worker <id>` and finish the update. Accepted and cancelled records are archived in `archive/workers/` and still count toward the limit. Organize or archive actual sidebar chats only when authorized.

`complete "<outcome>" --cursor <reviewed-cursor> --evidence "<coordinator evidence>" --remaining "<open items or none>"` closes a settled run and records its outcome. Use the cursor from the `status --full` snapshot you reviewed. If the run changed, review the new state and evidence before retrying. Claim goal success only after checking the integrated result against the parent criteria. If stopping without success, state that outcome and list unfinished work and verification gaps. If any worker was cancelled, `--remaining` is required. Keep the run open if work will resume. Use `status` to confirm closure after an interruption. Read `result`, `verification` (the coordinator's supplied text), and `remaining` together. Consult `archive/summary.md` after `status` reports `complete`. Use `clean` to archive already finished records from older runs. Follow the existing commit, merge, and push permissions.
