# Mini-Loop orchestration

The main chat owns the parent GOAL, worker assignments, decisions, and integration review. Workers own small, verifiable subgoals and report through shared project memory. Continue while verified progress is possible. Pause for a decision that changes scope, requires user authority, or resolves a blocker that the workers cannot handle safely.

## Start or resume

Resolve the application and initialize the independent sibling MLMS repository as described in the skill. Use Python 3.8 or later and run `python3 <skill-dir>/bin/orchestrate.py <checkout> <run-id> <command>` for the commands below. In a source checkout the helper is `orchestrate.py` at the repo root. Use a stable run ID and persist it with the parent GOAL in parent active context. The helper keeps `orchestration/<run-id>/run.json` under the canonical MLMS root with atomic updates under the shared lock.

- New run: use `init "<parent goal>"` and document how the parent GOAL will be verified. On resumption, use `status` on the same run. Never reset its budget or bypass a pause by initializing another run for the same GOAL.
- Split independent work into subgoals with expected outputs, testable criteria, prerequisites, and file ownership. Use linked worktrees when parallel edits could conflict. Verify that every worker resolves the same MLMS root before work. Keep dependent work queued in the parent's plan until its inputs are ready. Only the main chat dispatches workers.
- The limit is 100 chats per run including the main chat. Reserve one slot per new worker using `reserve <worker> "<subgoal>"` **before** asking the backend to start a chat. Reservations, closed chats, and cancelled reservations count throughout the run. Resume existing workers when practical. At the limit, continue with existing capacity or pause if a new chat is necessary. Up to three workers may hold active slices at once.

## Dispatch and monitor

- Use user-owned Codex chats when the user explicitly authorizes creating them for this work. Follow the available chat tool's authorization and worktree rules. Use the normal chat tools to organize registered chats and send assignments or follow-ups when authorized. Use native subagents when the user authorizes delegation to them. Keep work in the main chat when delegation is unavailable. Never assume one backend can interrupt a different backend.
- On creation, give the worker its subgoal, criteria, scoped checkout, run ID and worker ID, and tell it to wait for its registered assignment before changes. Once the actual handle is available, call `bind <worker> chat|subagent <handle> [--host <host>]`. For queued setup, retain the receipt and wait for the real handle; settle the existing reservation before retrying creation. Send the current epoch from `status` with each work assignment. A worker must run `begin <worker> <epoch>` before work; save the returned ticket. Keep the number of pending dispatches and active slices within the three worker slots.
- Each assignment covers one small slice. Before each editing or side effect batch, use `guard <worker> <ticket>`. When refused, finish only the checkpoint and end the turn. Acknowledge a pause as soon as safely possible. Avoid long-running commands that delay a checkpoint. Guard checks are cooperative and cannot stop a tool call already running.
- End **every** slice with `report <worker> <ticket> idle|blocked|candidate`, passing this JSON through stdin: `{"summary":"what changed","evidence":"checks, artifacts or commits","progress":"verified criteria met and remaining, plus confidence","next":"next small step, or none","blocker":""}`. Be explicit about missing checks. `candidate` requires evidence and means ready for main-chat review. `blocked` requires a reason. End the worker turn after the report and wait for dispatch from the main chat. Do not write directly into the parent's memory bank from a worker.
- Monitor registered workers using `status` and the backend's bounded wait or status tools while the main chat is active. Read new checkpoints and validate evidence before dispatching again. The helper keeps the three most recent checkpoints per worker so you can compare after resuming. Two consecutive slices on a subgoal without new verified evidence or a resolved blocker trigger review before further dispatch. Replan within scope when possible. If the user must decide, pause. Label missing or old reports as such. Use the count of verified criteria and remaining work for the progress estimate, with an honest confidence level.

## Pause all workers for a decision

1. Call `pause "<specific decision and reason>"` before requesting user input. This seals new reservations, new slices, and further guarded editing batches for this run. Stop dispatching and stop implementation in the main chat. Ask registered workers for their checkpoint and to end their turns using an authorized control channel. Workers that see the pause report without waiting for a separate message.
2. Give active workers one bounded wait for reports. If a worker keeps running, use its native interruption capability when available and authorized. For a sidebar chat without a direct interrupt tool, show its actual state and let the user stop it in the app if it cannot reach a checkpoint. Keep queued setup visible until it binds and stays idle or is confirmed cancelled. Only after the backend confirms a worker is no longer running may the main chat record `interrupt <worker> "<verified stop evidence>"` to settle a missing report; retain its previous checkpoint and mark it as potentially stale. Use `cancel <worker> "<reason and evidence>"` for out-of-scope work or confirmed failed setup. Never report an active or unverified worker as paused.
3. Ask the user **once in the main chat**, with the decision, options and tradeoffs, and one short line per affected worker giving its progress, evidence, blocker, and last known activity. Ask even if a stop is still unconfirmed, and identify any chat requiring manual interruption. Keep the run paused while waiting.
4. After an explicit user decision, confirm that affected chats are idle and queued creations have settled. Then record `resume "<actual user decision>"`. This advances the epoch so old assignments cannot start. Update parent decisions and dispatch with the new epoch. Elapsed time or silence does not authorize resumption.

## Accept and integrate

Review each `candidate` against its assignment, checks, and integration needs. If it needs more work, record `rework <worker> "<missing evidence or correction>"`. If accepted, write or update a concise, subgoal-keyed handoff in parent MLMS progress and sprint review under the shared lock, including result, evidence, and remaining integration work. Record `accept <worker> "<independent review and memory reference>"` only after the handoff is present. Update the same handoff on retry. Organize or archive completed chats only when authorized. Keep the assignment, last checkpoint and outcome in MLMS for resumption and audit.

Use `complete "<verified parent result>"` after settling or accepting all workers, evaluating the actual parent criteria, and updating the parent brief and memory. Follow the skill's existing commit, merge, and push permissions. The helper coordinates trusted workers through a shared record; it does not enforce process isolation or authorize app actions.
