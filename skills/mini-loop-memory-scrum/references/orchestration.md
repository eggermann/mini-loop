# Mini-Loop orchestration

This is the subgoal workflow within `auto`. The main chat owns the parent GOAL, assignments, decisions, and integration review. Workers report through shared project memory. Continue while verified progress is possible. Pause for a decision that changes scope, requires user authority, or resolves a blocker that the workers cannot handle safely.

## Start or resume

When the main chat handles subgoals itself, record scope, criteria, and handoffs in their Markdown contexts. Use the worker registry below for delegated work and to resume an existing registered run. Resolve the application and MLMS repository as described in the skill. Use Python 3.8 or later and run `python3 <skill-dir>/bin/orchestrate.py <checkout> <run-id> <command>`. In a source checkout the helper is `orchestrate.py` at the repo root. Persist the stable run ID with the parent GOAL in parent active context. The helper keeps `orchestration/<run-id>/run.json` under the resolved MLMS root with atomic updates under the shared lock.

- Use `init "<parent goal>"` before dispatching the first worker. Document the parent's verification criteria. To resume, use `status` on the same run for a compact view of open workers and keep its returned `cursor`. Preserve the run ID, pause, and chat count across resumption.
- Split independent work into subgoals with expected outputs, testable criteria, prerequisites, and file ownership. When delegation is authorized, dispatch independent subgoals with distinct branch/worktree assignments in parallel. Fill available slots before waiting and refill them as prerequisites are met. Keep dependent work queued until its inputs are ready, and run subgoals sequentially when edits cannot be isolated. Verify that every worker resolves the same MLMS root before work. Only the main chat dispatches workers.
- The limit is 100 chats per run including the main chat. Reserve one slot per new worker using `reserve <worker> "<subgoal>"` **before** asking the backend to start a chat. Reservations, closed chats, and cancelled reservations count throughout the run. Resume existing workers when practical. At the limit, continue with existing capacity or pause if a new chat is necessary. Up to three workers may hold active slices at once.

## Dispatch and monitor

- Use user-owned Codex chats when the user explicitly authorizes creating them for this work. Follow the available chat tool's authorization and worktree rules. Use the normal chat tools to organize registered chats and send assignments or follow-ups when authorized. Use native subagents when the user authorizes delegation to them. Keep work in the main chat when delegation is unavailable. Never assume one backend can interrupt a different backend.
- On creation, give the worker the parent goal in one sentence, its subgoal and criteria, scoped checkout, run ID and worker ID. Tell it to wait for its registered assignment before changes. Once the actual handle is available, call `bind <worker> chat|subagent <handle> [--host <host>]`. For queued setup, retain the receipt and wait for the real handle; settle the existing reservation before retrying creation. Send the current epoch from `status` with each work assignment. A worker must run `begin <worker> <epoch>` before work; save the returned ticket. Keep pending dispatches and active slices within the three worker slots.
- Each assignment covers one small slice. Before each editing or side effect batch, use `guard <worker> <ticket>`. When refused, finish only the checkpoint and end the turn. Acknowledge a pause as soon as safely possible. Avoid long-running commands that delay a checkpoint. Guard checks are cooperative and cannot stop a tool call already running.
- End each slice with `report <worker> <ticket> idle|blocked|candidate`, passing JSON through stdin. Use short entries such as `{"summary":"Added branch lookup","evidence":"resolver probe passed","progress":"2/3 verified","next":"check detached HEAD","blocker":""}`. Cite artifacts or checks when available. Keep full logs in their original output. `candidate` requires evidence and `blocked` requires a reason. End the worker turn with a brief receipt and wait for the next assignment. The main chat owns updates to the parent's Memory Bank.
- After the first snapshot, poll with `status --since <cursor>` to see only workers changed since the last poll. Use the new cursor for the next poll. Each row shows the subgoal, status, and latest checkpoint when available. Use `status --worker <id>` for one worker's history and `status --full` for the entire run including archived details. Use backend wait tools for live activity. Surface decisions, blockers, and verified outcomes in the main chat. Review the next assignment when two slices in a row show no new verified evidence or resolved blocker.

## Pause all workers for a decision

1. Call `pause "<specific decision and reason>"` before requesting user input. This seals new reservations, new slices, and further guarded editing batches for this run. Stop dispatching and stop implementation in the main chat. Ask registered workers for their checkpoint and to end their turns using an authorized control channel. Workers that see the pause report without waiting for a separate message.
2. Give active workers one bounded wait for reports. If a worker keeps running, use its native interruption capability when available and authorized. For a sidebar chat without a direct interrupt tool, show its actual state and let the user stop it in the app if it cannot reach a checkpoint. Keep queued setup visible until it binds and stays idle or is confirmed cancelled. Only after the backend confirms a worker is no longer running may the main chat record `interrupt <worker> "<verified stop evidence>"` to settle a missing report; retain its previous checkpoint and mark it as potentially stale. Use `cancel <worker> "<reason and evidence>"` for out-of-scope work or confirmed failed setup. Never report an active or unverified worker as paused.
3. Fetch a fresh `status` snapshot so unchanged affected workers are included. Ask the user once in the main chat, with the decision, options and tradeoffs, and one short line per affected worker giving progress, evidence, blocker, and last known activity. Identify any chat with an unconfirmed stop or requiring manual interruption. Keep the run paused while waiting.
4. After an explicit user decision, confirm that affected chats are idle and queued creations have settled. Then record `resume "<actual user decision>"`. This advances the epoch so old assignments cannot start. Update parent decisions and dispatch with the new epoch. Elapsed time or silence does not authorize resumption.

## Accept and integrate

Review each `candidate` against its assignment, checks, and integration needs. Use `rework <worker> "<correction>"` if it needs more work. Otherwise, write or update one line in the parent's `memory-bank/progress.md` under the shared lock with worker ID, subgoal, result, and evidence. Mention remaining integration work if any. Then call `accept <worker> "<independent review and memory reference>"`. The helper archives the full record in `archive/workers/`, takes it out of the normal snapshot, and keeps it counted toward the run limit. Cancelled work is archived too. Organize or archive actual sidebar chats only when authorized.

After settling all workers and verifying the parent criteria, update parent active context and run `complete "<verified parent result>" --remaining "<open items or none>"`. This writes `archive/summary.md` with the result, recorded decisions, and open items, and archives the run. Use `clean` to archive already finished records from older runs. Open and blocked workers keep their checkpoints. The archive lives under the same run directory in MLMS. Follow the existing commit, merge, and push permissions.
